# 卡片可视化编辑器的建模分析与改进路线

> 这份文档回答一个问题：**「可视化编辑卡片」这件事的本质是什么，当前实现离最优模型差在哪，下一步该怎么改。**
> 它不是 API 文档，也不重复 [business-rules.md](./business-rules.md) 的行为约定；
> 它描述的是*编辑器本身的模型*，用于判断后续每个功能该不该做、该以什么形态做。

## 1. 本质：卡片模板是一个「函数」，不是一份「文档」

一封告警卡片最终长什么样，完全由三件事决定：

```
AlertManager 消息  ──(数据)──▶  卡片模板（结构 + 变量绑定）  ──(求值)──▶  CardKit JSON  ──▶ 飞书渲染
        f 的输入                           f 本身                     f(data)              宿主的呈现
```

也就是说，**模板编辑器的本质是「编辑一个从数据到视图的纯函数 f」**，而不是编辑一篇稿子。
这条定义几乎能推导出所有已知的体验问题：

| 现象 | 根因（用「函数」视角看） |
|---|---|
| `${alerts_list}` 是个黑盒，用户不知道怎么改 | 函数体被压缩成了一个不可见的字符串 |
| 告警积木拖进去后「失忆」，标题变成组件类型名 | f 的节点没有稳定身份，只能靠**结构指纹**反推 |
| 循环 / 判断只能当「本地指令」塞进飞书 JSON | f 的控制流要寄生在宿主的数据结构里 |
| 不知道某个位置能填哪些变量 | f 的**参数类型**没有建模，作用域只存在于渲染代码里 |
| 组件数量、30KB 只有事后计数 | f 的**求值代价**没有建模 |
| 预览要靠来回切换页签 | 编辑的是 f 的源码，看到的不是 f(ctx) 的画面 |

**最佳模型的一句话结论**：
> 把编辑器建立成「**带类型的投影 + 显式 AST + 稳定节点身份**」，
> 让 CardKit JSON 退化为 AST 的**序列化目标**（落盘事实），
> 让画布变成「AST 在样本数据上的求值画面」（所见即所得）。

## 2. 当前实现的模型（as-is）

现在已经具备的、值得保留的骨架：

- **文档 = CardKit JSON 2.0 本身**（`card-builder/model.ts`）：没有第二套 DSL，画布 / 预览 / 发送同源，
  预览走 `POST /card-templates/preview`，发送走同一份 JSON —— 这是**正确且应当坚持**的决策。
- **本地指令**（`repeat` / `if`）：用「保存指令、服务端展开」的办法补上了飞书不支持的循环 / 判断，
  控制流第一次变成了可编辑的一等结构。
- **类型化的数据契约**：`RenderContext` + `meta.variables`（含 `item.*` 作用域）+ `build_context`，
  服务端已经是「数据 → 变量表」的权威。
- **组件目录驱动 UI**：面板 / 属性表单 / 校验全部由 `card_catalog` 下发，前端不另立规则。
- **位置感知的变量面板**：`variablesFor(variables, inLoop)` 已经是最小可用的类型检查。

当前模型的缺口（也正是第 1 节表格里的根因）：

1. **AST 不存在**：树就是 `body.elements` 的 JSON，控制流指令和展示组件混在同一个 `tag` 命名空间，
   编辑器只能靠 `tag` 字符串猜语义。
2. **节点身份不稳定**：积木身份靠结构指纹（`presets.ts`），用户改一个字段就「掉身份」；
   复制 / 升级 / 命名都没有稳定的锚点。
3. **变量是字符串**：`${...}` 只是文本，没有绑定对象、没有类型、没有来源路径，
   校验只能在渲染时把未知变量变成空串。
4. **求值代价没有模型**：`repeat` 展开 ×N 的代价只体现在一个全局「展开约 N」计数器上。
5. **画布不是渲染器**：画布画的是「结构框 + 语法文本」，真正的视觉要切到预览。

## 3. 目标模型（to-be）：带类型的投影

### 3.1 三层职责

| 层 | 内容 | 谁负责 | 落盘位置 |
|---|---|---|---|
| **数据层（Schema）** | 分组 / 代表告警 / `alerts[]` 的字段与类型、作用域（`group` / `alert` / `item`） | 服务端 `build_context` + `/meta` | 不落盘（每次请求下发） |
| **结构层（AST）** | Layout（Section / Columns / Collapse / Divider）、Control（Each / If）、Leaf（Text / Button / Image） | 编辑器内存模型 | 序列化成 CardKit JSON（现状）+ `builder_meta`（身份/命名） |
| **呈现层（Render）** | 画布上「真实外观」的预览 | 同构渲染器（编辑器 + 预览共用契约） | 不落盘 |

### 3.2 AST 的形态（关键设计）

```
Node =
  | { kind:'element', tag:'markdown'|'div'|'button'|..., props }      // 展示组件，opaque 透传未知 tag
  | { kind:'each', source:'alerts', maxItems?, empty?:Node[], body:Node[] }   // 持久化为 repeat
  | { kind:'if', when:Expr, negate?, body:Node[] }                     // 持久化为 if
  | { kind:'columns', columns:Node[][] }                               // 持久化为 column_set
Text  = InlineToken[]        // [{literal}|{var:'item.summary', type:'string'}]
```

四个要点：

1. **控制流是 AST 节点，不是 `tag` 碰巧叫 `repeat`**：`Each` / `If` 与展示组件在类型上分开，
   展开、计数、作用域推导、序列化都以节点类型分派，不再靠字符串比较。
2. **文本是 inline token 列表，不是魔法字符串**：`${item.summary}` 在模型里是一个带 `type` 与
   `sourcePath` 的绑定；编辑器渲染成不可拆的「胶囊」，插入/删除/校验都是结构操作，
   拼写错误在编辑期就能报（而不是渲染成空串）。
3. **未知组件是 opaque 节点**：用户从搭建工具导入的 `chart` / `table` 原样保留，
   保证「JSON 逃生舱」永远可用。
4. **节点有稳定 id**：`builder_meta`（与 `card_json` 平级）保存 `{ nodeId → {label?, presetId?, note?} }`，
   **不污染 card_json**，后端不需要为此做任何剥离；老模板没有 meta 时回退到现在的指纹推断。

### 3.3 求值代价与约束建模

- `cost(node)` 在 AST 上是可计算的：`element=1`，`columns=Σ`，`if=max(0, branch)`，
  `each = min(items, policy, maxItems) × cost(body)`。
- 由此得到三个能力：**节点级代价提示**（「这里最多展开 100 个组件」）、
  **保存前的前置校验**（超 200/30KB 直接定位到超限节点）、
  **自动收缩建议**（超出时提示把 `max_items` 调到 N）。
- 现在只有全局计数器；改成节点级后，「为什么卡片超限」是可解释的。

### 3.4 同构渲染器（所见即所得）

- 目标不是 100% 复刻飞书渲染，而是**同一套「渲染契约」**：
  服务端渲染器与编辑器画布对同一棵 AST 输出同一套结构（区别只在字体/间距等宿主细节）。
- 最低成本版本：画布直接用 markdown 渲染 `${alerts_summary}` 这类样本数据（现在显示的是语法字符），
  颜色 / 按钮 / 分栏按飞书语义近似；差异处标注「以飞书为准」。
- 收益：用户不必「切到预览页签再回来」，编辑-反馈闭环从分钟级降到秒级。

## 4. 改进清单（按 价值/成本 排序）

### P0 —— 低成本，直接消灭当前痛点

| # | 项目 | 状态 |
|---|---|---|
| 1 | **变量胶囊化**：文本字段里的 `${var}` 渲染为胶囊（可用 / 越权 / 未知三态 + 悬停说明） | ✅ 已落地（`model.ts` `classifyVariable` / `variableTokensInText`，属性面板渲染胶囊） |
| 2 | **节点身份落盘**：`card_message.builder_meta.labels`（`element_id → 名称`），指纹推断作为回退 | ✅ 已落地（属性面板「节点名称」；拖入积木时自动记名；移动 / 复制后仍跟随） |
| 3 | **结构大纲面板**：左栏「结构」缩进树，点击定位 | ✅ 已落地（`Outline.tsx`） |
| 4 | **代价前置**：节点级「展开约 N 个组件」+ 超限标红 + 保存前拦截（工具栏已拦） | ✅ 已落地（循环节点提示 + 诊断面板） |
| 5 | **诊断面板**：未知变量 / 循环外 `item.*` / 空循环体 / 容量超限，逐条可点击定位 | ✅ 已落地（`analyzeCard` + Builder 面板） |

> 已完成的部分都没有引入新的落盘格式：诊断、代价、胶囊、大纲全部是**内存视图**，
> 落盘仍是 CardKit JSON。剩下最值得做的是第 2 项（身份）与 §3.4 的同构渲染。

### P1 —— 中等成本，明显提升上限

6. **数据面板（拖字段）**：右栏把 Schema 渲染成一棵树（分组 → 代表告警 → `alerts[i] → labels/annotations`），
   拖字段到文本字段 = 插入绑定；只显示当前位置合法的字段。→ 让「变量」从背单词变成拖拽。
7. **参数化积木**：积木从「一段固定 JSON」升级为「带参数的片段」
   （例如告警行：选图标、字段顺序、分隔符、是否显示概要行），参数化后仍是 AST 片段。
8. **预设/片段库 + 局部应用**：把常用结构存成命名片段，可插入、可覆盖、可比较。
9. **结构 diff**：保存前展示「这次改了什么结构」（新增/移动/删除节点），而不是 JSON 文本 diff。
10. **真实预览**：把 3.4 的渲染契约往前推一步，画布直接显示近似最终效果。

### P2 —— 大改，架构级收益

11. **AST 成为显式内存模型 + 双向序列化**：`JSON ⇄ AST` 两个方向都有测试；
    未知组件 opaque 透传保证无损。此时控制流、作用域、容量、身份全部有类型支撑。
12. **模板版本化与差异**：以结构为单位存档，可回滚到「某个节点的某个版本」。
13. **服务端渲染契约同步**：`expand_card_json` 与前端 AST 求值共用同一份「指令语义」规范
    （现在两边各写一遍：`repeat`/`if` 的字段、真值规则、上限规则）。

## 5. 明确不建议做的事

- **不要在磁盘上引入第二套 DSL**：AST 是编辑器的视图，落盘仍是 CardKit JSON；
  一旦落盘变成自有格式，预览 / 发送 / 导入导出就会出现第二个真相源。
- **不要做绝对定位的自由画布**：飞书卡片是流式布局，自由摆放会产出宿主表达不了的版面，
  最终必然退化成一堆 column_set 拼凑。结构树 + 流式画布才是与宿主同构的交互。
- **不要试图 100% 复刻飞书渲染**：收益递减；正确做法是「同构到组件与样式语义」+ 差异提示。
- **不要隐藏 JSON 页签**：它是唯一的逃生舱（未收录组件、宿主新能力）。
  但它的定位应降级为「调试 / 高级」，而不是并列的一等编辑方式。
- **不要把编辑器元数据塞进 `card_json`**：宿主对未知字段会直接报错，
  且会让「JSON 就是事实」变得不干净；放 `card_message.builder_meta` 这类兄弟字段最稳。

## 6. 三步落地

| 阶段 | 交付 | 可独立验证的验收 |
|---|---|---|
| **第一步（1–2 周）** | P0 全量：胶囊、`builder_meta`、结构树、代价、诊断 | 新模板不再「失忆」；未知变量在编辑期报错；超限能定位到节点 |
| **第二步（2–4 周）** | P1：数据面板、参数化积木、结构 diff、近似真实预览 | 用户不写 `${}` 也能搭出常见告警卡；预览与发送一致 |
| **第三步（1–2 月）** | P2：AST 双向、版本化、前后端语义同源 | JSON 与画布任意切换无损；指令语义有单一规范与测试 |

每一步都能独立上线、独立回滚，且都不改变**落盘格式**（第三步也只是把 CardKit JSON 作为
AST 的一个序列化目标继续保留）。

## 7. 当前实现与本模型的映射

| 模型要素 | 现状 | 差距 |
|---|---|---|
| 数据层 Schema | `build_context` + `meta.variables`（含 `item.*` 作用域） | 没有按路径的完整字段树（只到注解/标签的通配） |
| 控制流 AST | `repeat` / `if` 本地指令 + 服务端展开 | 仍是 `tag` 字符串；缺显式节点类型 |
| 节点身份 | 结构指纹 + **`builder_meta.labels` 持久名称** + 「转为循环」 | 只有显式命名 / 拖入的节点有名字；循环体内不可命名 |
| 变量绑定 | 文本 `${}` + 位置感知下拉 | 无类型、无来源路径、无胶囊 |
| 容量建模 | 全局「展开约 N」+ **节点级展开代价** | 保存前只拦截，未做自动收缩建议 |
| 诊断 | **诊断面板**（未知变量 / 越权 / 空循环 / 超限，可点击定位） | 后端 `validate` 与前端诊断尚未共享同一份实现 |
| 渲染一致性 | 画布结构框 + 预览页签 | 不是同一套渲染 |
| 语义同源 | 后端 Rust 展开 + 前端预估各写一遍 | 缺一份共享的指令语义规范 |

> 结论：现有实现已经把最危险的两件事做对了——**单一事实来源（JSON）** 和 **服务端展开**。
> 下一步的最优解不是推倒重来，而是**在编辑器里补上缺失的模型**（AST、绑定、身份、代价），
> 并把「预览」升级为「画布本身就是预览」。这样每一层都有类型支撑，功能才会从「打补丁」变成「可推演」。
